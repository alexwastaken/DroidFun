# USB setup and updates in app 0.5.0

## Current customer troubleshooting (App 0.9.0)

Use **Connection → Run diagnostics** for read-only checks and a reviewed local support report. **Show test pattern** is a temporary live-display check on connected droids, including factory and swapped-wiring units; it does not install firmware. See [customer diagnostics and owner triage](SUPPORT.md). Generic firmware recovery remains limited to verified supported standard legacy boards; factory, newer, custom and unidentified devices need the correct Workshop/support service. Older installation and temporary-sketch acceptance records below are historical, and do not authorize generic reinstalls on current factory units.

App 0.5.0 embeds normal firmware **1.2.3** and a separate temporary display-test sketch. Choose Meep, Boo or Claw and connect a USB data cable. Connection scans every two seconds. An RP2040 in USB setup mode appears as **Set up your bot**. Choose **Set up droid**, keep USB connected, and wait for the restart and protocol handshake. Existing running bots have an **Update droid** button that requests a software restart, then installs the bundled UF2. App settings are retained; a successfully installed new board replaces the older USB selection. Ordinary firmware updates retain the 256 KiB saved-playlist partition.

On Macs running macOS 13 or later, the bundled universal picotool helper uses the ROM's direct USB interface. The helper and its libusb dependency include both Apple Silicon and Intel slices. Discovery reads USB descriptors without accessing the mounted drive. Installation validates the selected ROM USB identity and RP2040 flash identity, checks an expected board identity when updating a running bot, writes only the embedded firmware, and requires readback verification. It then waits for the same flash identity to return as a serial controller. A blank board can omit its flash ID from picotool's device information. First setup permits that case only with exactly one ROM device before checking and again before writing, followed by exactly one new runtime serial identity. Known-board updates still require a matching flash ID. The helper requires no separate installation or Terminal use. Its [source archives, licenses and offline rebuild recipe](../src-tauri/resources/picotool-macos-universal/README.md) accompany the app resources.

Manual **Scan USB** shows a visible scanning state followed by a persistent result: a detected bot, a board ready for setup, no device, or a scan error with next steps. Automatic discovery continues every two seconds. A completed installation refreshes the runtime port list before showing its result.

On a Mac with direct USB setup available, **Install display test** is available for a board in setup mode, and **Run display test** is available when normal firmware reports a display fault. The app checks this capability before requesting a restart; the test action stays hidden when support cannot be confirmed. This installs the bundled temporary sketch with readback verification. The sketch independently tests the standard GP4/GP5 wiring, 0x3C/0x3D addresses, SSD1306 and SH1106 patterns, and emits an identity-checked JSON report. The app pauses its normal protocol connection during the test. **Restore normal software** requests a USB restart without opening the case, then reinstalls the bundled normal firmware. Successful display writes still require a physical screen check.

Windows and Linux use a validated mounted RP2040 boot drive; a Mac without an available direct helper also falls back to this route. It checks the mount and exact INFO_UF2 identity, rejects host folders and symlinks, and only touches RPI-RP2 volume names on Mac. Neither route writes during discovery or automatically flashes a device. Scans, restart preparation, diagnostic reads and installations have timeouts; a stalled transfer must not imply a successful installation. Direct USB child processes are canceled and reaped on timeout. A canceled filesystem worker checks cancellation before starting a write after a blocked operation.

Restart preparation, installation, diagnostic reads and manual connection share an operation guard. A native driver call can outlive its caller's timeout, so its worker retains that guard until it returns. A timed-out restart leaves the normal connection paused. Cancellation checks run between native reset calls, with a best-effort return to 115200 baud if the 1200-baud step has been issued but the operation cannot finish. This cannot undo a reset already accepted by the board; the app asks the user to reconnect and scan rather than claiming the board stayed unchanged.

The board returning as a serial device confirms restart, not a working display. The normal connection handshake verifies the board identity and OLED health. A board that reports an I2C error shows a screen fault and cannot save a wall-power playlist. Firmware 1.2.2 retains the two standard SSD1306 address checks introduced in 1.2.1 on GP4/GP5. It also fixes a one-byte overflow when rejecting an oversized malformed COBS packet. The regression tests check identity preservation and recovery into a valid frame. This correction has not been established as a fix for the USB interruptions described below. Firmware cannot repair missing power, bad soldering, incorrect pins or a damaged panel.

For finished customer units, install firmware before final assembly and physically confirm readable screens over USB and after a power cycle. Consumers should receive a working bot; an internal hardware fault requires service or replacement. The app's USB setup flow does not replace that acceptance check.

Local acceptance: the first Meep installed firmware 1.2.0 through the app on October 24, 2026. On the next retry, the app restarted it with the case closed. The Mac stalled on the mounted ROM drive, while the vendor USB interface remained responsive. The app's direct USB installer subsequently installed firmware 1.2.1, and a fresh handshake matched that board's identity and reported firmware 1.2.1 and OLED i2c_error. This establishes a powered, running board; display communication still fails with firmware that checks both supported OLED addresses. The owner had reported that the screen had never worked. A working physical screen remains unestablished and requires hardware inspection/service.

The first direct installation displayed an incorrect completion error because the app expected a text marker that `picotool load -v` does not print. The completion check now uses successful exit of the fixed load-and-verify command; upstream reports verification mismatches as failures. The device's fresh firmware handshake remains a separate acceptance step. On October 25, the final installed app completed the entire **Update droid** flow in one action: restart, direct write with readback verification, automatic reconnection, firmware 1.2.1 handshake, and the message “USB setup is complete. Your bot responds, but its screen needs attention.” No manual Connect action was needed on that final run. Discovery also distinguishes runtime and ROM product/class descriptors because both can share VID/PID, and picotool selection uses the flash identity rather than the shared ROM USB serial.

On October 25 a second Meep arrived in ROM setup mode with no flash ID in `picotool info -d`. The previous app rejected it as unidentified. The corrected app displayed **Bot found — ready for setup**, installed the display-test sketch through its own button, verified the flash, and read a matching report from the second board. That report detected the screen at 0x3C and confirmed successful writes. The owner confirmed a visible checkerboard and that the screen was on. This is a different board from the earlier I2C-error unit.

The app then restored normal firmware 1.2.1 with the case closed. After reconnecting USB, its normal handshake reported OLED ready, and the owner confirmed the enabled happy-face widget was physically visible. USB stability remains unresolved: a 30-second read-only IORegistry observation saw repeated device removal/re-enumeration and missing serial ports. During a subsequent 20-second check with DroidFun closed, the board remained absent from the Mac's device list. These observations establish working display/software but do not identify the cause of the USB interruptions. Cable/port comparison is the next physical check. The app now clears stale installation-success text when the connection is lost.

For the 0.4.2 release, firmware 1.2.2 compiles with Arduino-Pico 6.3.0, and all four firmware host-test executables pass with address/undefined-behavior sanitizers: storage, lifecycle, OLED addresses and packet bounds. Frontend checks, release-tooling checks, package verification and Windows/Linux installed-package smoke checks passed. Coverage includes cancellation and operation-guard lifetime after a timeout. The universal Mac package passed architecture and ad-hoc signature checks, and Mac/Windows updater signatures were verified. The Mac Scan USB interface also showed a persistent **No bot found** result with next steps.

The universal helper's arm64/x86_64 slices, macOS 13 minimum load commands, signatures and local version/help execution were checked during its build. Those checks do not establish Intel hardware or macOS 13 runtime acceptance. A subsequent in-app update installed firmware 1.2.2 on the second Meep with the case closed. The app verified the returning identity and reported OLED ready; the owner confirmed a readable physical face or usage screen. A 30-second read-only observation still saw USB re-enumeration, so that screen/update success does not establish sustained connection stability. A brief scan/handshake disagreement now shows **Reconfirming USB connection…** instead of simultaneously saying no bot was found; update controls wait for a matching current port.

A later 90-second passive observation, with DroidFun closed and no DroidFun process running, produced 46 valid samples. It recorded five USB registry IDs and the board was absent after 24 seconds. The disappearance can therefore occur without an active DroidFun process. This does not identify the cause or establish that a cable, port, board or firmware change would fix it; USB stability remains unresolved.

The next check reported it up to date. The board was absent during that acceptance run, so no successful physical USB connection after the desktop upgrade was observed. Remaining acceptance includes sustained USB stability, physical USB operation after the desktop upgrade, saved-playlist power-cycle behavior, and Intel Mac/macOS 13/Fedora runtime checks. Windows/Linux installer smoke checks do not establish operation with a physical bot. Mac packages remain ad-hoc signed without Developer ID notarization, and Windows installers lack platform code signing. A finished consumer unit still requires a readable screen and a physical power-cycle check; the published app and its passing build checks do not replace that hardware acceptance.

## Powered standby and waking the computer

Install the app update, then under Connection choose **Update droid** once to install 1.2.3. A powered Meep, Boo or Claw now shows a fallback face if there is no desktop connection, including USB sleep and long host inactivity. Saved text/face playlists take priority over the default face. Automatic dim/off timers are removed; manual screen-off and configured quiet hours remain intentional controls. The app remembers the selected USB board ID and reconnects after it returns, even if the serial path changes. Keep the app running in the background for automatic recovery; start-at-login is available in Settings. Sleep can remove USB power on some computers or hubs, in which case the bot boots to its face or saved screens when power returns.

Normal setup displays plain steps and names each remembered droid. Technical connection and display-test tools are under **Help and connection details**. In 0.10.0, plug in up to four programmed droids and use **Previous droid**, **Next droid** or the **Selected droid** menu at the top. Each retains its own screens and display settings. Other powered droids use their firmware fallback face or saved screens; only the selected droid receives live app frames. A fifth waits for a slot until another droid is unplugged. Slots remain stable across USB enumeration and selection changes, and are enforced by native selection and discovery. Older remembered profiles are preserved separately and do not count as attached droids. New unprogrammed droids are prepared in Workshop one at a time.


## Mac display-sleep smile

While the app runs, it reads the power state of all online Mac displays once per second. When every display is asleep, the selected powered droid shows its built-in smile instead of its live widget. The playlist position and pause/pin choice are kept, and waking a display restores the current screen automatically. An awake external monitor keeps live widgets active when a laptop lid is closed. Manual screen-off and quiet hours retain priority. This state is temporary; it does not change saved droid profiles.

The app reads Core Graphics display-power metadata only; it does not capture the screen, lock the Mac or change system sleep settings. Full computer/USB sleep is handled by firmware 1.2.3's existing powered fallback. The droid still needs USB power. Saved standalone playlists remain the owner's chosen offline behavior. No firmware replacement is required for the Mac display-only sleep trigger.
